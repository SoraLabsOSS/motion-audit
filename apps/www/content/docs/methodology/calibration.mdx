# Methodological Foundations, Epistemic Status, and Calibration Targets

## 1. The Three-Layer Methodological Architecture

SoraLabs Motion Audit structures its methodology across three distinct epistemological layers to ensure scientific reproducibility, clarity of assumptions, and intellectual independence:

```text
Chromium / W3C Standards
       ↓
[Layer 1] Theoretical Foundations (Physical Pixel Math & General Ordering)
       ↓
[Layer 2] Browser-Derived Heuristics (CDP Signals & Observable Mechanics)
       ↓
[Layer 3] Empirical Calibration (Benchmark Targets & Discriminatory Weights)
       ↓
SoraLabs S-to-F Engine
```

---

### Layer 1: Theoretical Foundations

The first layer is grounded in established browser, graphics, and web-platform specifications and rendering architecture:

- **Pixel Density & Backing Store Estimation:** Under the standardized RGBA8888 backing-store model:
  $$\mathcal{M}_{\text{raw}} = W \times H \times 4 \times \text{DPR}^2$$
  _Precision Notice:_ This represents a **theoretical raw texture-memory estimate** rather than a claim about the complete runtime GPU memory footprint (which also accounts for alignment, driver padding, surfaces, and compositor overhead).
- **Qualitative Rendering Pipeline Ordering:** Browser rendering architecture establishes a general qualitative cost hierarchy:
  $$\text{Compositor-only} < \text{Paint-triggering} < \text{Layout-triggering}$$
  SoraLabs relies on this platform-derived ordering as the physical baseline for its quantitative model.

---

### Layer 2: Browser-Derived Heuristics

The second layer translates browser architecture into observable, quantifiable diagnostic signals:

- **Invalidated Surface Area:** Tracking paint rectangle geometry relative to viewport bounds.
- **Invalidated Surface Area:** Tracking paint rectangle geometry relative to viewport bounds.
- **Tiled Layer Modeling:** Chromium's tiled compositor architecture allocates memory in discrete $256 \times 256$ tiles via `cc::TileManager`. Scroller layers allocate additional raster tiles covering the visible viewport plus a pre-paint raster lookahead horizon.
- **Timeline Concurrency Modeling:** Evaluating active animation density across time intervals, balancing sustained mean concurrent load against peak coordination bursts.

---

### Layer 3: Empirical Calibration Parameters

The final layer contains parameters that cannot be derived from browser specifications alone. Thresholds and weighting functions in production performance tools are calibration decisions rather than universal mathematical constants.

Key empirical calibration parameters include:

- Layout thrashing base penalty: $\mathcal{P}_{\text{layout}} = 5$ (Chromium frame-budget baseline: calibrated against forced reflow overhead)
- Style thrashing base penalty: $\mathcal{P}_{\text{style}} = 2$ (Blink tree-walk recalculation factor: ~40% of reflow cost)
- Mount/Init phase deduplication ceiling: $\le 15$ pts (framework hydration lifecycle allowance)
- Micro-interaction duration threshold: $\mathcal{T}_{\text{duration}} = 100\text{ms}$ (Google RAIL instantaneous perception boundary)
- Viewport normalized weights: Animations 0.35, Scroll 0.25, Thrashing 0.25, GPU 0.15 (with pipeline bottleneck coupling)
- Desktop Tier S VRAM ceiling: $\mathcal{V}_{\text{desktop\_S}} = 64\text{MB}$ (Power-of-two GPU texture allocation pool)
- Scroller raster lookahead: Chromium cc::PictureLayerTiling lookahead ratio (1.5x)
- Concurrency model: Weighted active timeline concurrency evaluation (0.6 mean + 0.4 max)
- GPU score synthesis: Piecewise operational band interpolation (40% texture VRAM + 40% layer count + 20% tiled scroller backing)

**Empirical Protocol & Revision Notice:**
These values represent initial calibration targets designed to achieve stable separation between the S/A/B/C/D/F performance tiers based on physical GPU allocation limits and Google RAIL thresholds.

_Calibration parameters are explicitly distinguished from web-platform facts and may be revised as the benchmark corpus, browser graphics architectures, and validation protocols evolve._

## 3. Reference Viewports and Initial Calibration Targets

### Canonical Viewports:

- **Desktop Reference:** $1440 \times 900\text{px}$, Reference Density: $\text{DPR} = 2$ ($4\times$ pixels).
- **Mobile Reference:** $390 \times 844\text{px}$, Reference Density: $\text{DPR} = 3$ ($9\times$ pixels).

> **Modeling Boundary Notice:**
> Raw texture memory and tiled backing-store estimates are reported as separate modeled quantities and must not be interpreted as additive measurements of physical VRAM without accounting for browser implementation details.

### Continuous Score & Tier Boundary Continuum:

The aggregate scoring function continuously maps measurements into a normalized $[0,\, 100]$ score. Discrete tier boundaries represent project-defined operational bands, not universal industry standards. Values falling between bands contribute progressively to the continuous aggregate score. In the current implementation, Tier F means an aggregate score below $10$; explicit pillar bottleneck caps can still limit a score above that boundary.

> **Interpretation boundary:** Motion Audit is a standards-informed, browser-observable diagnostic algorithm. It combines theoretical estimates, Chromium-derived signals, and project-specific calibration. It is not an official W3C, Chromium, Lighthouse, Core Web Vitals, or industry certification score, and it should be used for comparative analysis under a defined test environment rather than as an absolute claim about user-perceived performance.
